## 3. Architecture (researched, chosen — bibliography at §7)

**Server: vertical slices + typed errors.** Modeled on cal.com's `packages/features/<domain>`
(each domain folder owns its logic, services, repositories, DTOs, UI-facing API, and tests;
cross-feature imports only through a public API — enforced by lint) with Effect-style
`TaggedError` failure classes at the boundaries (the pattern OpenRouter/OpenCode/Warp use).
One Node process, one SQLite file, repository pattern for data access, thin route handlers.
Language: TypeScript strict. Lint/format: Biome (cal.com's choice — one tool, fast).

**Client: the shadcn ownership model — which is literally our copy-first doctrine.** Components
are owned source, not dependencies: copy from the captured Cursor/Devin code into our tree and
chisel. Behavior primitives (dialogs, menus, keyboard/focus) come from Radix; styling is
Tailwind with design tokens as CSS variables, exactly as the originals do it. No invented
visuals, ever.

**Data/sync: Linear's lesson** — a change log is cheap to write and expensive to serve. Our
server keeps an append-only run/event log per automation (like Linear's sync action log);
clients checkpoint and replay deltas. Last-write-wins; no CRDTs. This is what makes run-history
and live-updating UI fast without websockets complexity.

**Agent execution model (for our own product's automations): Replit Agent's discipline** —
smallest-possible-task per agent, isolated working copies, checkpoint before every mutation,
human review gate before apply. An automation run is: trigger → plan → execute in isolation →
checkpoint → report. (Our trigger engine itself is a thin Loop-client: a run is a conversation
with Linear Agent, which is free — see MASTER-PLAN §3.)

## 4. Testing doctrine (replaces "50,000 sloppy tests")

- **Playwright e2e for critical journeys only** — connect-Linear, create-automation,
  edit-automation, view-run, chat-gate. Test user-visible behavior with role/label/text
  locators (never CSS structure), isolated contexts, pre-authenticated storage state.
- **Unit/coverage: cal.com's rule** — ~80%+ on new/changed code, CI-enforced, no global quota
  theater.
- **Every PR must be verified in a real browser by the agent before opening** — screenshot +
  interaction pass with Computer Use against the served app, compared to the captured original.
  A PR without a verification artifact does not get reviewed, let alone merged.
- Flakes are P0 and get fixed immediately, never retried into green.

## 5. Agent workflow (how we work from here)

- **Planning phase (now):** agents produce plans, maps, and comparisons — no implementation PRs.
- Branch protection stays on; every change via PR.
- **CodeRabbit** reviews every PR (`.coderabbit.yaml` committed): auto-review on open+push,
  `@coderabbitai autofix` to auto-apply fixes, `@coderabbitai fix-ci` for CI failures. It is the
  first reviewer; humans second.
- Agents never mark their own PR ready — an orchestrator (Runner) verifies the evidence links,
  the CU verification artifact, and the tests, then flips it.
- One idea per PR. If a PR touches two features, it gets split.
